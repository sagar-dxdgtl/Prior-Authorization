## §1. Why plan-string matching cannot settle a row

Every number here was measured live on 2026-07-29.

**Neither side carries a shared key.**

| side | carries a plan identifier? |
|---|---|
| Oscar FL portal plan labels | **0 of 65** |
| AZ Blue network labels | **0 of 23** |
| Real cached 271 `planCoverage` strings | **0 of 7** |

Tier 1 (identifier match) is the only tier that may license an OUT_OF_NETWORK. On commercial/ACA pairs it
is *structurally unreachable*, so no matcher — LLM or otherwise — can produce a decisive verdict from names.

**Same payer, same member, same plan, different vocabulary:**

```
Oscar's 271 says   : "BASE SILVER CSR 150"  /  "SILVERSIMPLEPCPSAVER"
Oscar's own portal : "Silver Simple PCP Saver CSR 150"
verbatim match     : False        match_plan() -> None (declines)
```

**The client's `Insurance` column names a payer, a line, sometimes a state — almost never a network.**
Run through the real tokenizer, all 11 Test 3 rows reduce to the payer name or the state.
`"UHC Medicare Advantage GA"` survives as `[]` — nothing. Only `"UHC Commerical NHP Access HMO"` names a
real network (it maps to UHC's `NHP HMO/POS Access`), **and our matcher cannot see it** — see defect D3.

**The format is not stable between deliveries.** The same client sent `"UHC Medicare Dual Complete
AZMCARE"` (names a product *and* a market code) and `"UHC Medicare Advantage GA"` (names nothing below the
line of business). A fixed parser cannot work.

**Test 3 has no member id and no DOB.** It is provider-side only, so **no 270 can be fired from the sheet
at all** — members are entered live at demo time. The Insurance string is not a degraded fallback to the
271; at load time it is the only plan information that exists.

## §2. What actually works — provider-first reverse lookup

**Fetch the provider once and read the complete set of networks they participate in.** The member's plan
then becomes a filter applied *afterward*, not a prerequisite.

Why it wins:

* One fetch, no per-network fan-out.
* Sidesteps §1 entirely — never needs the plan string to name a network.
* **In no network ⇒ decisive OON** for everything that payer sells.
* **In every candidate ⇒ decisive IN**, so plan ambiguity stops mattering (proved on Molina row 8).
* Cacheable per provider; contracts change slowly.

### Verified per payer

| payer | platform | profile lists networks? | NPI search? | TIN? |
|---|---|---|---|---|
| Oscar | private JSON directory | **yes** — `offices[].network_infos`: `provider_network_id` + `tin` + `in_network` + start/end dates | yes | **yes** |
| AZ Blue | HealthSparq | **yes** — "Plans accepted → Medical Networks" | **no** (name only) | no |
| Molina | Zelis Sapphire | **yes** — "Plans/Programs Accepted" | yes | no |
| UHC | Find Care guest | **no** — read the result LIST instead | yes | in the `locationId` URL param |
| Cigna | hcpdirectory | not yet checked | **no** (name only) | no |

Oscar's is richest: one fetch returns participation for **every** network with effective dates, so it can
answer "in-network *on the date of service*". Field is `provider_network_id` — reading `network_id`
silently yields `None`.

## §4a. Row 3 resolved — effective dates break source conflicts

The Oscar-vs-TiC contradiction on row 3 was **not** a conflict of fact. Oscar's `network_infos` carries
start/end dates, and the full history for Sanders (NPI 1700846789, TIN 921600050, net 065) reads:

```
2019-02-06 → 2026-01-26   in_network = False    (seven years OUT)
2026-01-27 → 2026-12-31   in_network = TRUE     <- contract STARTS
2027-01-01 → (open)       in_network = False    <- contract TERMINATES
```

The TiC MRF was built **before 2026-01-27**, so it correctly recorded a physician gap *at that time*.
**The sources disagreed about the date, not the fact.**

### The reconciliation rule this yields — better than REVIEW

| portal | TiC | check | conclusion |
|---|---|---|---|
| IN | absent | is `start_date` **after** the MRF build date? | yes ⇒ recent addition; **TiC stale, portal wins** |
| absent | present | is there an `end_date` in the past? | yes ⇒ termination; **TiC stale, portal wins** |
| IN | absent | `start_date` is old | genuine conflict ⇒ **REVIEW** |

Deterministic, and it converts a whole class of REVIEWs into answers. **Requires recording the MRF's build
date at ingest** — we do not currently store it.

### Two consequences bigger than row 3

**1. TiC lag is systemic.** Any provider contracted inside the MRF's staleness window reads as a **false
OON** from TiC. That is a standing risk on every commercial row answered from an MRF — including rows 5
and 11, both of which are currently TiC-sourced.

**2. The verdict must be date-of-service scoped.** All seven of Sanders' offices flip to `in_network=False`
on **2027-01-01** — five months out. "Is he in-network?" has no answer without "on what date". A system
reporting a bare "IN" today would be **wrong** for a January procedure. Oscar is the only source we have
that exposes this; the portals show a point-in-time badge with no dating.

**Participation is per-OFFICE.** All seven of his Oscar offices are in-network, but with two different start
dates (2026-01-27 and 2026-05-15) — the apparent True/False overlap was offices whose contracts had not yet
begun. ⚠ The sheet's clinic (**6880 Douglas Blvd, Douglasville 30135**) is **not among Oscar's seven listed
offices**, though all seven carry the sheet's TIN. Directory incompleteness or a genuinely different site —
undetermined. Note `3525 George Busbee Pkwy NW, Kennesaw 30144` IS listed, which is Manayan's clinic from
rows 1 and 10 (Georgia UVC Medical LLC).

## §5a. The liveness principle — ALREADY IMPLEMENTED, better than proposed

Four portals mislead on result counts and BCBS IL returns nothing at all, so a **manual** walk needs a
control query (a common surname that must return results) before any absence can be read as OON. That is a
rule for *humans driving a browser*, and it is how rows 5, 6 and 10 were validated today.

**The drivers already enforce the equivalent, and more strictly** — audited 2026-07-29, no change needed:

* `uhc_findcare.py` — OON only when `count > 0 AND plan_confirmed`; zero results → UNKNOWN, noting "an
  empty result set does not distinguish out-of-network from a failed search".
* `bcbsil_provider_finder.py` — OON requires `read.real` (not a fuzzy substitution or hard empty) **and**
  `read.complete` (whole set on screen, not page 1 of a paginated set) **and** `read.plan_code ==
  plan_code` verified *in the results URL*. `if not read.real: continue  # Never an OON (trap 1)`.
* `humana_finder.py`, `wellcare_hub.py`, `oscar_care_options.py`, `molina_provider_search.py` all carry
  docstrings naming this exact failure mode and guard against it.

**A non-empty result set IS the liveness proof** — no separate control query is needed in code, because a
populated set demonstrates the search ran. Positive results are self-validating either way: a hit proves it.

## §6. A wrong conclusion, and why it was wrong

Worth reading before trusting any directory experiment.

Same search under `AARP Medicare Advantage GA-5 (HMO-POS)` and under `UHC Nursing Home Plan GA-F001
(PPO I-SNP)` produced **byte-identical result PDFs except the clock** (160 lines; `16:57` vs `16:59`), and
the profile badge read In-network on **5 of 5** plans tested. That was concluded to mean *UHC Find Care is
plan-blind*.

**It was wrong.** One more search settled it — `NHP HMO/POS Access`, same location, returned **1** provider
against Medicare's **13**. The search *is* network-filtered. The real explanation: **UHC's 12 GA Medicare
plans share one GA Medicare network.** SNP designations govern member eligibility and benefits, not
necessarily the provider network.

> **Method lesson: identical results across same-line plans is evidence of a SHARED NETWORK, not a broken
> filter. Vary the LINE OF BUSINESS before concluding a directory ignores the plan.** Five Medicare plans
> agreeing looked overwhelming and was worth nothing; one commercial plan settled it.

Consequence: the profile badge is **untested, not disproven** — under the shared-network reading it was
correct each time. To actually test it, open a provider's profile under a plan whose *result list* excludes
them. Until then, **read the result LIST, never the badge.**

## §7. Code defects found today — all unfixed

**~~D1~~ — WITHDRAWN. Not a defect; I misdiagnosed it.** `uhc_findcare.py` never reads the profile badge
(zero matches for `In-network` / badge / `provider-details` in the file). It reads the **typeahead
suggestions and result cards** — exactly the surface the "fix" would have moved it to. The premise was
the plan-blind claim already retracted in §6; since the search IS network-scoped,
`presence_verdict(plan_confirmed=True) → IN_NETWORK` is correct as written.

**D2 — FIXED 2026-07-29 (TDD).** `parse_271.py:189` leaked the employer name into the plan slot.
`plan_name = selected or planName or groupDescription`. When the payer returns a junk `planCoverage`
(Cigna returned literally `"Network"`, which `_JUNK` drops), `groupDescription` wins. Verified live:
`plan_string_from_271` → `'DISNEY WORLDWIDE SERVICES, INC.'` — an **employer name** typed into a payer's
public search box and written to the capture's audit note. Degrades safely today (no token match →
UNKNOWN) but is wrong in principle. `groupDescription` must never reach the plan slot.

**D3 — FIXED 2026-07-29 (TDD).** `plan_match.py` could not see `NHP Access HMO`.
`NHP` is 3 characters (below the 4-char floor in `distinctive_tokens`) and `ACCESS` sits in
`_NON_DISTINCTIVE`. That is **row 4's network name** — the one Insurance string in the whole sheet that
does name a network, and we are blind to it. Note `healthsparq.py` already uses a 3-char floor for exactly
this reason ("PPO"/"HMO"/"EPO"); the shared matcher does not.

**D4 — FIXED 2026-07-29 (TDD), and it was NOT what it looked like.** "The baked-in list is stale" was
the symptom; investigating found the live harvest still works (100 raw links → 24 networks) and two real
bugs underneath:

* **Label drift produced a SELF-TIE.** The gate prints `Statewide / National PPO + Prosano`; the baked-in
  map had `Statewide/National PPO + Prosano`. `_network_map` keyed the merge on the raw label, so one
  network appeared **twice**, `_best_network` correctly refused the tie, and **both spellings resolved to
  None** — a member on that plan could not be pinned at all. Fixed by merging on `_label_key()`
  (punctuation/case-insensitive), live label winning. `_merge_networks` extracted so it is testable
  without a browser.
* **`_GATE_LINK_RE` truncated labels at the first escaped quote.** AZ Blue publishes
  `Blue Preferred Care Tiers (\"Triple Choice Plan\" for State of AZ employees)` and we captured
  `Blue Preferred Care Tiers (\` — discarding the only tokens that distinguish that network, so a State
  of AZ employee could never match on them. Label group now accepts JSON escapes; `_gate_label()` decodes.

The fallback map was then re-harvested from the live gate (24 networks). Note the gate publishes
`Neighborhood` **and** `Neighborhood (All counties except for Maricopa and Pima)` with an identical
product/brand/prefix — one network under two labels, because the gate is now coverage-type-scoped and a
network recurs under several types. Kept verbatim.

**D5 — FIXED 2026-07-29 (TDD).** The market-code regex missed real plan codes. `_MARKET = r"\b([A-Z]{2}-\d{1,4})\b"` requires digits
only after the dash. UHC's FL AARP plan list contains `FL-001P`, `FL-MA01` and `FL-MA2` — **three of seven
codes invisible to it** (it catches FL-35, FL-0006, FL-0025, FL-0031). These are exactly the identifiers
that make tier-1 matching work on the Medicare line, which is the *one* line where identifiers converge.
Same shape as D3: we are blind to identifiers the payers actually print.

**Not a defect:** `plan_benefits` rows that look duplicated are distinct `segment_id`s (8,081 rows,
8,081 distinct plans).

**Not a defect (test-suite trap):** a plain `pytest` run shows **10 failures that are all

## §7a. `provider_participation` — started, first defect fixed (2026-07-29, TDD)

**We already had the table.** `provider_network_facts` (0025) carries
`payer_key · npi · tin · in_network · source · plan · network_name · effective_date · retrieved_at`,
so the reverse lookup extends it rather than duplicating it.

**Defect found and fixed: a provider's network SET collapsed to one row.** `uq_pnf_identity` and
`ProviderNetworkStore.upsert` both keyed on `(tenant_id, payer_key, npi, tin, source)` — **without
`network_name`**. Oscar returns Sanders' participation across three networks from ONE fetch
(065 IN, 082 OUT, 083 OUT; same payer, NPI, TIN and source), which is *one row* under that key. So:

* only the first network survived, and
* **which one survived depended on iteration order** — reversed, the store keeps `082 False` and drops
  `065 True`, turning an in-network provider into an out-of-network answer.

The OUT rows are not noise: "in none of this payer's networks" is what makes an absence decisive, and
that needs every network's fact.

`network_name` is now part of the identity, in the model, in `upsert`, and in migration
**`0037_pnf_network_identity`**. Note `uq_pnf_identity` is a **UNIQUE INDEX** created by raw SQL in
0025, *not* a table constraint — `op.drop_constraint` cannot see it and a `pg_constraint` lookup
returns nothing. 0037 uses 0025's `DROP INDEX IF EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS` idiom.
Verified from zero on a throwaway DB and round-tripped (6-col → 5-col → 6-col).

⚠️ **`preauth_test` was NOT stamped.** It sits at `0033` like the shared DBs; the index change was
applied to it directly with SQL so the tests can run, leaving `alembic_version` untouched. Stamping it
to 0037 would break the demo branch if it shares that database.

**Dated participation — DONE (migration `0038_pnf_effective_dates`).** `start_date` / `end_date` (real
DATE columns) and `source_built_at` (TIMESTAMPTZ, the source's own build date — distinct from
`retrieved_at`, which is when *we* wrote the row). `facts_for(..., as_of=<date>)` scopes a read to a
date of service, and **undated facts are always returned**: a NULL means "undated", never "expired",
so a TiC or portal fact is not silently dropped when a date is supplied.

**§4a is now code — `domain/fact_reconcile.py`.** `reconcile_network(facts)` returns
`agreed | stale_source | review | single_source | no_facts` with a human-readable reason.
**Recency is deliberately NOT the rule**: "the newer source wins" is wrong whenever the newer source
is merely less complete. Only a contract that *began after the other source was built* explains a
disagreement; absent that, the answer stays REVIEW.

**A second collapse, caught only by running real data end-to-end.** After 0037 the store still lost
facts: a network has a **TIMELINE**, and net 065's three periods (OUT to 2026-01-26, IN from
2026-01-27, OUT from 2027-01-01) share a `network_name`. They collapsed to one row and the **expired**
period won, leaving net 065 with no fact effective today. `start_date` is now part of the identity too
(model, `upsert`, and the unique index in 0038). Same defect as 0037, one level down — the unit tests
passed throughout; only the end-to-end run exposed it.

Verified against live Oscar data: **19 dated facts from one profile fetch**, net 065 reads False on
2025-06-01, True today, False on 2027-01-15, and the row-3 directory-vs-TiC conflict now arbitrates
itself to `in_network=True (stale_source)` with the dates quoted in the reason.

## §3a. Sourcing strategy, by line of business — what the day converged on

| line | how to pin the plan | how to get the provider's networks |
|---|---|---|
| **Medicare** | 271 contract number → `plan_benefits` → exact portal label. Deterministic, built (§3) | portal result list (UHC), or profile plan list where offered |
| **Commercial** | **no usable plan string** — measured (§1) | **TiC per-network MRF membership** — ingest each network and test the NPI |
| **Medicaid** | no identifier exists at all | portal profile (Molina), or state Medicaid enrollment `Plans Accepted` (verified on GA and FL) |

State Medicaid enrollment files turned out to be a genuinely good source: authoritative, government-run,
and they carry a `Plans Accepted` column naming the MCOs. They answer **Medicaid only** — CMS publishes
nothing equivalent for Medicare Advantage, whose networks are private contracts.

**Do NOT build the LLM plan-string crosswalk.** §1 is the measurement that killed it. Tier 3
(`portal/plan_llm.py`) stays as-is: off by default, confidence "medium", unable to license an OON.
