Branch `feat/live-portal-capture`, based on `main`, **not pushed** (no upstream). 821 offline tests pass
(`python -m pytest tests/ -q -m "not live"`). Nothing here is on `main` or the demo branch yet.

Read this top to bottom before touching the portal package. The single most important thing in it is the

## 1. Priorities, worst exposure first

### P1 — `payers/adapters/oscar.py::resolve_network` can assert a wrong OUT_OF_NETWORK
**This is shipped production code, not a new driver.** It licenses an OUT_OF_NETWORK off a ~0.6-recall
*name* match. Every name-matching defect removed from the drivers on 2026-07-28 was this same class:
a same-surname stranger, or a partial-name match, read as our provider. It is the only place in the
system that can currently tell a user something confidently wrong.

Do it the way the drivers were done: read the adapter, its callers and its tests, prove the defect with
a failing case first, then fix. Do not patch it blind — it has existing callers.

### P2 — the TiC signal reads a different store than the one TiC data is ingested into
`domain/tic_network.tic_network_status()` → `domain/tin_crosswalk.default_crosswalk()` (an **in-code
seed**). Ingested MRF data lands in the **`provider_network_facts`** table. They are not the same store.

Proof, live on the dev DB (5433/preauth): `provider_network_facts` holds **16 in-network rows** for
payer `oscar-fl-south-florida`, TIN `463812940`, source `tic`. Yet the resolver's own corroboration
prints:

> "Billing TIN 463812940 **not found** in oscar-fl-south-florida's Transparency-in-Coverage MRF"

Three consequences:
1. A **false statement in an audit trail** — the note asserts the opposite of what the database holds.
2. The **physician-OON-from-TiC** path can never fire while credentialing exists, because the resolver
   short-circuits on credentialing before reaching the `provider_network_facts` roster check.
3. Every future MRF ingest lands somewhere the signal cannot see, so **fix this before pulling more
   MRFs** or the pull is silently inert.

`resolve_provider_network` *does* read `provider_network_facts` for its physician-OON branch
(`default_provider_network_store().facts_for(payer, tin=...)`), but only when `cred is None`. Decide
deliberately whether `tin_crosswalk` should read through to `provider_network_facts`, or whether
`tic_network_status` should consult both.

### P3 — route Medigap / Original Medicare away from network directories
Discovered by chasing a real discrepancy. The Test 2 Roulhac row (NPI 1801837109, Humana CO) is
**Original Medicare + Humana Medicare Supplement (Medigap)** — there is *no provider network*, so a
Medicare-participating provider is in-network by definition. The saved proof is a **Medicare.gov Care
Compare** screenshot showing "Charges the Medicare-approved amount", i.e. accepts assignment — not a
Humana network listing.

Asking a network directory about a member who has no network can only produce UNKNOWN or a false OON.
`domain/enrollment.pecos_enrollment` and `domain/line_of_business` already exist; what is missing is the
branch that recognises the Medigap/FFS case and skips the network check entirely. Likely affects more
rows than this one.

## 2. TiC / TIN applicability — check this BEFORE looking for an MRF

**Transparency in Coverage is commercial-only. Medicare Advantage, Medicaid and Dual are federally
exempt — no MRF exists for them, and TIN is not the operative key.** This is already encoded as
`_EXEMPT = {"medicare", "medicaid", "dual", "federal"}` in `domain/provider_network.py`, where TiC is
marked **N/A rather than blank** for those lines. Treat a missing MRF for an exempt line as *correct*,
not as a gap to fill.

## 3. Oscar TiC MRF — the path, and a repo note that is wrong

`docs/payer-sources/ma-regional.json` says Oscar's TiC URL is *"a landing page (state-specific PDFs) not
a CMS-schema JSON index."* **That is incorrect** — probably recorded from a non-JS fetch, since the page
is JS-rendered and WebFetch sees only the shell. Drive it with Playwright.

`https://www.hioscar.com/transparency-in-coverage-files/oscar` links **49 monthly CMS-schema indexes**:

```
https://hioscar-cms-tic-us-east-1.s3.amazonaws.com/oscar/20260701_oscar_index.json   (~970KB, current)
```

That index holds 54 reporting-structure entries and **2,823 distinct in-network files**. Filter hard —
**2,774 are Optum behavioural carve-outs and 18 are Davis Vision**. Oscar's own *medical* files are:

```
…/oscar/negotiated_rates/<YYYYMMDD>/oscar/<YYYYMMDD>-oscar-<NNN>-in-network.json
```

**`<NNN>` is Oscar's `networkId`** — `070` is exactly the network the Oscar driver reads back as
`networkId=070` in its results URL. So network → MRF file is a direct one-to-one mapping, and you need
*one* file per network rather than a trawl.

To pull GA: get Georgia's networkId(s) from `https://www.hioscar.com/search/networks/` (**returns HTML,
not JSON — needs a browser**), fetch the matching numbered file, then
`python scripts/ingest_tic.py <file> <out.csv> --payer oscar`. Files are large; `--limit N` exists. The
`.env` residential proxy is there because some MRF CDNs are US-geo-locked.

Do **P2 first** or the ingested rows will be invisible to `tic_network_status`.

## 5. Cigna — what is and isn't verified

Verified live: the full walk (entry → location → category → guest gate → 10 plans → pinned → banner),
and `_force_medical`. That last one mattered — the search landed on `/cbh-providers` with
`providerGroupCode=B` (**behavioural**) while the same URL still carried the correctly pinned *medical*
plan as `medicalProductCode=OAP&medicalEcnCode=OA001`. `providerGroupCode=P` is the medical group
(`M` renders Cigna's own "Maintenance Notice"). Without that retry the driver could only ever return
UNKNOWN, which for a physician is every time.

**Not verified end-to-end:** the plan-codes confirmation and the radius hint. The third live walk in ten
minutes was refused by Cigna's **F5 BIG-IP ASM** (rate-related; the driver detected it, returned BLOCKED,
and correctly noted no challenge was offered and nothing was bypassed). One clean run at human pace
closes both.

**To make Cigna decisive you need the product name** ("Open Access Plus" vs "Choice Fund OA Plus" vs
"OA Plus" are distinct entries among the 10 offered). Commercial employer plans have no Medicare
contract number and no ACA HIOS id, so `plan_match` gets a token match at best.

## 6. Things that will waste your time if you don't know them

- **Roster payer keys are market-qualified.** `cigna-healthcare-fl-south-florida`, `oscar-ga-atlanta`,
  `unitedhealthcare-ga-atlanta`, `bcbs-empire-anthem-elevance-hcsc-il`, `molina-healthcare-tx-dallas`
  (Fort Worth is DFW), `wellcare-centene-ga-atlanta`. **7 of 9 portal targets shipped with keys matching
  no roster row**, so `driver_for()` resolved nothing; keys are now derived from `roster_seed`.
- **Both databases are stamped `0033_portal_facts_resync`** — the *demo* branch's head — so
  `alembic upgrade`/`current` fails on any main-based branch. DDL for this branch's `0028`/`0029` was
  applied directly and both are idempotent. **Re-chain migrations at rebase**; `0028`/`0029` collide with
  the demo branch's numbers.
- `tests/conftest.py` `setdefault`s db tests to **5432/preauth_test**, a *different instance* from the dev
  DB on **5433/preauth**. Apply schema to both.
- **A launchd agent cannot reach `~/Desktop`** (macOS TCC: `getcwd: Operation not permitted`). Grant Full
  Disk Access to the executing binary or move the repo. Session token limit resets **04:10 IST**.
- `python -m playwright install chromium` is separate from `pip install -e .`.
- The UA is derived from `browser.version` — do **not** hardcode it again. A declared Chrome/131 against a
  real Chromium 149 is a false claim and is exactly what Aetna's Akamai edge rejects.

## 7. Boundaries — settled, do not relitigate

- **No CAPTCHA solving, no fingerprint patching, no stealth plugins, no auth bypass.** Challenges are
  detected, screenshotted and reported as BLOCKED; a blocked payer routes to its CMS-mandated public FHIR
  directory. The 2026-07-28 probe found **0 challenges across all 9 portals**, so this rarely arises.
- **Human-scale volume.** One lookup per provider, never enumerate or page. If a payer starts refusing,
  stop — do not retry around it. Cigna's F5 refusal was self-inflicted by three walks in ten minutes.
- **No member PHI reaches a portal** — provider name + clinic ZIP only. `from_271.py` deliberately
  excludes `EligibilityResult.group`: in this client's data that column holds member identifiers
  (`SRGB10057830`, `101601541800`), and the plan string is both typed into a public search box and stored
  in the audit note.
- **Absence is not OON.** No confirmed plan → UNKNOWN. Empty result set → UNKNOWN. Possibly-truncated set
  → UNKNOWN. Only "results returned, ours absent, plan confirmed" is an OUT_OF_NETWORK.

## 8. The lesson worth carrying

Every one of the six drivers reviewed over-claimed **in the same direction**: a capture note asserting
something the code had not established. Six for six is a design gravity, not six mistakes — which is why
the walk trail is recorded in its own `portal_captures` column and why every OON gate is phrased to drop
into the note so a reader sees *which* guard fired.

Two second-order findings worth keeping:

- **The deepest bugs were in shared code, not the drivers** — 7 of 9 targets with dead payer keys, and
  `plan_match` understanding only Medicare-shaped identifiers (blocking every ACA row). Neither would
  have surfaced from reading either file; they appeared because eight drivers hit them from eight angles.
- **Tests get less sensitive exactly as the code they cover gets safer.** Wellcare's mutation harness
  silently weakened: once every path returned UNKNOWN, assertions on the resulting *status* stopped
  distinguishing a working gate from a broken one. Assert the gate, not just the verdict.

`git log --oneline main..HEAD` is the full record; every commit message states what was verified live
versus what is assumed.
