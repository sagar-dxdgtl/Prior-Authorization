## 1. Priorities, worst exposure first

### P1 — `payers/adapters/oscar.py::resolve_network` can assert a wrong OUT_OF_NETWORK
**This is shipped production code, not a new driver.** It licenses an OUT_OF_NETWORK off a ~0.6-recall
*name* match. Every name-matching defect removed from the drivers on 2026-07-28 was this same class:
a same-surname stranger, or a partial-name match, read as our provider. It is the only place in the
system that can currently tell a user something confidently wrong.

Do it the way the drivers were done: read the adapter, its callers and its tests, prove the defect with
a failing case first, then fix. Do not patch it blind — it has existing callers.

### P2 — the TiC signal reads a different store than the one TiC data is ingested into
`domain/tic_network.tic_network_status()` → `domain/tin_crosswalk.default_crosswalk()` (an **in-code
seed**). Ingested MRF data lands in the **`provider_network_facts`** table. They are not the same store.

Proof, live on the dev DB (5433/preauth): `provider_network_facts` holds **16 in-network rows** for
payer `oscar-fl-south-florida`, TIN `463812940`, source `tic`. Yet the resolver's own corroboration
prints:

> "Billing TIN 463812940 **not found** in oscar-fl-south-florida's Transparency-in-Coverage MRF"

Three consequences:
1. A **false statement in an audit trail** — the note asserts the opposite of what the database holds.
2. The **physician-OON-from-TiC** path can never fire while credentialing exists, because the resolver
   short-circuits on credentialing before reaching the `provider_network_facts` roster check.
3. Every future MRF ingest lands somewhere the signal cannot see, so **fix this before pulling more
   MRFs** or the pull is silently inert.

`resolve_provider_network` *does* read `provider_network_facts` for its physician-OON branch
(`default_provider_network_store().facts_for(payer, tin=...)`), but only when `cred is None`. Decide
deliberately whether `tin_crosswalk` should read through to `provider_network_facts`, or whether
`tic_network_status` should consult both.

#### P3 — DONE, and the branch now grades on ASSIGNMENT (2026-07-28)

`no_network_verdict` exists and the Medigap/FFS case never reaches a network directory. Two things
were wrong underneath it, both found by running the live path rather than by reading the code:

**1. The branch was inert on the live path.** `has_provider_network` matched `plan` and
`benefit_type` as one blob, but they are not equal evidence. `benefit_type` is a coarse tag on a
payer *row* — `humana-co-denver` is tagged **Medicare Advantage** because that is what Humana mostly
sells in Denver, not because this member bought it. So the tag's "Advantage" beat an explicit
"Medicare Supplement" plan and skipped the whole branch for the one row it was built for. The plan
now settles it alone; the payer tag is only a fallback. **Every existing test passed
`benefit_type=None`, which is exactly why this survived — the live path never passes None.**

**2. The docstring and the code disagreed about the fact being checked.** The rule was always
stated correctly — *"a provider who accepts Medicare assignment is in-network by definition"* — but
the code checked PECOS **enrollment** and then returned `confidence="high"`. Enrollment is necessary,
not sufficient. It cannot tell these three apart, and they do not cost the member the same thing:

| | CMS source | Member's exposure | Verdict now |
|---|---|---|---|
| Participating (`ind_assgn = Y`) | National Downloadable File | Medicare-approved amount | IN, high |
| Non-participating (`ind_assgn = M`) | National Downloadable File | up to the 115% limiting charge; only Medigap **Plan F/G** cover Part B excess | IN, medium, flagged |
| Opted out | Opt Out Affidavits | private contract — Medicare pays **nothing**, so the supplement pays nothing | **OON, high** |

`enrollment.assignment_status(npi)` reads both, opt-out first (it outranks a stale `Y`), date-range
checked because the affidavit file retains expired rows and bare presence would be a false OON.
Confidence is only "high" when the opt-out file was actually *reached* — an unchecked negative is
not a clear one. Where PECOS and the Care Compare file contradict each other the result is REVIEW.

Live-verified 2026-07-28: **`mj5m-pzi6`** is the Care Compare backing file (3,387,942 rows) and
`ind_assgn` has **no "N" value** (Y: 3,131,543 / M: 256,399 / N: 0) — so a provider missing from it
is UNKNOWN, never "does not accept assignment". NPI 1801837109 → `ind_assgn=Y`, no affidavit →
**IN_NETWORK / high**, which is the same fact the saved Care Compare screenshot shows.

#### The opt-out check also applies to Medicare Advantage — DONE (2026-07-28)

An opted-out provider cannot be in an **MA** network either: the affidavit is a private contract and
an MA organisation may not pay them outside emergency or urgently needed care. That covers most of
Test 2 and Test 3, so `enrollment_negative` now consults the opt-out file for `medicare`/`dual`
alongside the PECOS check. Two things this needed beyond the obvious:

* **It had to be moved out from behind the `cred is None` guard.** `enrollment_negative` only ran
  when the clinic had *no* credentialing row — so the check was skipped on exactly the rows it
  matters on. A credentialing matrix is the clinic's own admin record and is the source most likely
  to be stale here, because an affidavit is filed with **CMS and never with the plan**.
* **CMS does not silently overturn contract evidence.** Credentialing IN + a current affidavit →
  **REVIEW / conflict**, consistent with the existing precedence rule, and the safer error: flipping
  to OON off a monthly file that may be weeks stale over-claims in the other direction. Credentialing
  OON + affidavit simply agree. No credentialing row → plain OON.

The display signal was changed with it: PECOS alone would have printed a green **ENROLLED** beside
that OON, because an opted-out provider *is* still Medicare-enrolled. Both statements are true and
together unreadable, so the affidavit takes the row (`OPTED_OUT`, danger).

**Live-verified on a provider the enrolment check cannot catch.** Most opted-out providers are also
absent from the Order-and-Referring file, so PECOS fires first and the opt-out path never shows —
which would have made this look like it worked when it hadn't been exercised. NPI **1548271240**
(opted out 12/28/2015–12/28/2027, *and* still order/refer eligible, so `pecos_enrollment → True`)
returns **REVIEW** with credentialing IN and **OUT_OF_NETWORK** without it. In a 4,000-row sample of
the affidavit file, **2,832** were still order/refer eligible — so this overlap is the common case,
not an edge one.

> request. Both reach OON, and spending a second call to refine an already-correct decisive answer
> is not worth it. `test_a_confirmed_not_enrolled_still_wins_and_skips_the_extra_lookup` pins that.

**2,774 are Optum behavioural carve-outs and 18 are Davis Vision**. Oscar's own *medical* files are:

```
…/oscar/negotiated_rates/<YYYYMMDD>/oscar/<YYYYMMDD>-oscar-<NNN>-in-network.json
```

**`<NNN>` is Oscar's `networkId`** — `070` is exactly the network the Oscar driver reads back as
`networkId=070` in its results URL. So network → MRF file is a direct one-to-one mapping, and you need
*one* file per network rather than a trawl.

To pull GA: get Georgia's networkId(s) from `https://www.hioscar.com/search/networks/` (**returns HTML,
not JSON — needs a browser**), fetch the matching numbered file, then
`python scripts/ingest_tic.py <file> <out.csv> --payer oscar`. Files are large; `--limit N` exists. The
`.env` residential proxy is there because some MRF CDNs are US-geo-locked.

Do **P2 first** or the ingested rows will be invisible to `tic_network_status`.

## 6. Things that will waste your time if you don't know them

- **Roster payer keys are market-qualified.** `cigna-healthcare-fl-south-florida`, `oscar-ga-atlanta`,
  `unitedhealthcare-ga-atlanta`, `bcbs-empire-anthem-elevance-hcsc-il`, `molina-healthcare-tx-dallas`
  (Fort Worth is DFW), `wellcare-centene-ga-atlanta`. **7 of 9 portal targets shipped with keys matching
  no roster row**, so `driver_for()` resolved nothing; keys are now derived from `roster_seed`.
- **Both databases are stamped `0033_portal_facts_resync`** — the *demo* branch's head — so
  `alembic upgrade`/`current` fails on any main-based branch. DDL for this branch's `0028`/`0029` was
  applied directly and both are idempotent. **Re-chain migrations at rebase**; `0028`/`0029` collide with
  the demo branch's numbers.
- `tests/conftest.py` `setdefault`s db tests to **5432/preauth_test**, a *different instance* from the dev
  DB on **5433/preauth**. Apply schema to both.
- **A launchd agent cannot reach `~/Desktop`** (macOS TCC: `getcwd: Operation not permitted`). Grant Full
  Disk Access to the executing binary or move the repo. Session token limit resets **04:10 IST**.
- `python -m playwright install chromium` is separate from `pip install -e .`.
- The UA is derived from `browser.version` — do **not** hardcode it again. A declared Chrome/131 against a
  real Chromium 149 is a false claim and is exactly what Aetna's Akamai edge rejects.

## 6c. State Medicaid enrollment — the bar a source has to clear

`medicaid_enrollment(npi, state)` feeds `enrollment_negative`, which asserts **OUT_OF_NETWORK** on a
confirmed miss (you cannot be in a Medicaid MCO's network for a programme you are not enrolled in).
That is the strongest claim this codebase makes from a public source, so a state is only wired when
its source clears two bars:

1. **Identifier-grade** — the NPI comes back in the response, so the match is confirmed *client-side*.
   A server-side NPI filter whose output we cannot check is trust, not evidence.
2. **Authoritative for the state** — its own enrolled-provider file, not one MCO's network directory.
   Absence from a single MCO says nothing about enrollment.

**Wired:** `NY` (Socrata), `IL` (HFS individual-provider directory), `ME` (MaineCare FHIR R4, anon
read). All three verified live in both directions on 2026-07-28.

**The two that look wireable and are not:** `KS` answers cleanly but returns `NPI: null` on every
row; `TX` (TMHP OPL) returns HTML with the NPI encoded. Neither match can be confirmed. The other
~18 evaluated states each carry their reason in `_MEDICAID_UNWIRED` — browser postback, CAPTCHA, a
provider *name* we do not carry, or a bulk import. Unwired states report that reason and return
**undetermined**; they never guess.

> Worth knowing for the Meridian IL row: HFS says Petermann **is** enrolled in IL Medicaid, so the
> negative filter correctly does not fire. The staff **OON** for that row comes from the MCO's
> network, not from enrollment — which is exactly the split this section is about.

## 7. Boundaries — settled, do not relitigate

- **No CAPTCHA solving, no fingerprint patching, no stealth plugins, no auth bypass.** Challenges are
  detected, screenshotted and reported as BLOCKED; a blocked payer routes to its CMS-mandated public FHIR
  directory. The 2026-07-28 probe found **0 challenges across all 9 portals**, so this rarely arises.
- **Human-scale volume.** One lookup per provider, never enumerate or page. If a payer starts refusing,
  stop — do not retry around it. Cigna's F5 refusal was self-inflicted by three walks in ten minutes.
- **No member PHI reaches a portal** — provider name + clinic ZIP only. `from_271.py` deliberately
  excludes `EligibilityResult.group`: in this client's data that column holds member identifiers
  (an alpha-prefixed `SRG########` and a 12-digit numeric), and the plan string is both typed into a public search box and stored
  in the audit note.
- **Absence is not OON.** No confirmed plan → UNKNOWN. Empty result set → UNKNOWN. Possibly-truncated set
  → UNKNOWN. Only "results returned, ours absent, plan confirmed" is an OUT_OF_NETWORK.

## 8. The lesson worth carrying

Every one of the six drivers reviewed over-claimed **in the same direction**: a capture note asserting
something the code had not established. Six for six is a design gravity, not six mistakes — which is why
the walk trail is recorded in its own `portal_captures` column and why every OON gate is phrased to drop
into the note so a reader sees *which* guard fired.

Two second-order findings worth keeping:

- **The deepest bugs were in shared code, not the drivers** — 7 of 9 targets with dead payer keys, and
  `plan_match` understanding only Medicare-shaped identifiers (blocking every ACA row). Neither would
  have surfaced from reading either file; they appeared because eight drivers hit them from eight angles.
- **Tests get less sensitive exactly as the code they cover gets safer.** Wellcare's mutation harness
  silently weakened: once every path returned UNKNOWN, assertions on the resulting *status* stopped
  distinguishing a working gate from a broken one. Assert the gate, not just the verdict.

`git log --oneline main..HEAD` is the full record; every commit message states what was verified live
versus what is assumed.
